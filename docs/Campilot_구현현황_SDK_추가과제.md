# Campilot 구현 현황·SDK·추가 과제

기준: 2026-11-15, 현재 소스 코드 및 확인된 실행 결과.
이 문서는 초기 기획안 및 이전 구현 보고서와 차이가 있을 때 현재 구현 상태를 설명한다.

## 1. 이번 변경
- 차박지 이동 중 내비 안내를 종료해도 ‘차박 시작’을 제공한다.
- 조건: 차박지 이동 단계, 도착 알림 또는 안내 종료, 처리 중인 경로 요청 없음, 미확인 경로 없음, 최신 차량 정보와 P단.
- 수동 시작은 실제 목적지 도착으로 기록하지 않는다. navigationArrived=false를 유지한다.
- 수동 시작 후에는 ‘주차한 곳에서 쉬는 중이에요’로 표시한다.
- ‘다시 안내받기’도 유지한다.
- 충전소 도착 및 귀가 완료 조건은 이번 변경 대상이 아니다.

## 2. 전체 흐름
앱 시작 → Pleos 현재 위치 표시 → 사용자가 추천 요청 → 목업 차박지 3곳 중 선택 → Pleos 내비의 집 주소 확인/등록 → 다음날 집으로 출발할 시간 선택 → 전력 계획 확인 → 필요 시 충전소 경유, 아니면 바로 출발 → 실제 내비 안내 → 도착 또는 안내 종료 시 Campilot 복귀 요청 → 주차 후 차박 시작 → 잔량·예상 잔량·수동 공조 화면 → 귀가 경로 요청 → 귀가 완료.

실제 내비의 ‘안내 종료’ 후 Campilot 큰 화면 복귀는 이전 작업에서 계측 테스트 외 실제 앱 UI로 확인했다. 실제 도로 주행에 따른 목적지 도착 이벤트와 자동 복귀는 아직 재현하지 않았다.

## 3. 기능별 상태

| 기능 | 구현 상태 | 실제 연동과 제한 |
|---|---|---|
| 현재 위치 | 구현 | NaviHelper 현재 위치/주소 조회. Android LocationManager나 Google 위치 API를 쓰지 않는다. 에뮬레이터의 내비 공급자가 반환한 위치이며 실제 차량 GPS 실차 검증과는 구분한다. |
| 차박지 추천 버튼·목록·선택 | 구현, 데이터는 목업 | 솔숲·호수·별빛 3곳의 고정 목록. 현재 위치에 따라 실제 주변 장소를 검색·정렬하는 추천은 아직 아니다. 시설·거리·좌표도 시연 데이터다. |
| 귀가할 집 | 실제 SDK 연동 | HOME 즐겨찾기 조회, 주소/좌표 확인, 미등록 시 실제 내비 집 등록 화면 연결, 복귀 후 재조회. 여정 내 확인 정보는 ViewModel 메모리에 둔다. |
| 귀가 출발 시각 | 구현 | 현재 기기 시각 표시, 다음날 09/10/11시 및 직접 시간 선택. 집 도착 시간이 아니라 차박지에서 출발할 시간이다. |
| 전력 계획 | 가정 모델 구현 | 이동·차박·귀가·예비 배터리 10%를 합산하고 추가 충전량·출발 목표 잔량을 표시한다. 실제 전력 소비 예측 모델은 아니다. |
| 배터리·주차 상태 | 실제 SDK 연동 | Vehicle SDK로 SOC와 P단을 조회한다. 앱 표시 중 약 5초 주기 갱신, 10초를 넘긴 값은 중요 동작에 사용하지 않는다. |
| 충전 판단·경유 | 프로토타입 구현 | 부족 전력에 따라 고정 목업 충전소를 실제 내비 경유지로 전달한다. 실제 충전소 검색·가용성 조회·충전 시작/종료 제어는 없다. |
| 실제 내비 실행 | 구현·확인 | 목적지/경유지 요청, 안내 상태 확인, 내비 전면 요청. ROUTE_GUIDING 모드로 안내를 판별한다. 응답 미확인 시 수동 경로 확인 절차를 유지한다. |
| 안내 종료 후 앱 복귀 | 구현·UI 확인 | SDK 종료 이벤트 수신 후 기존 Campilot Activity를 전면으로 요청한다. 이동 중 foreground service로 앱 동결을 방지한다. 복귀 후 서비스 정리도 확인했다. |
| 도착 감지 | 코드 구현·실제 도착 미검증 | 목적지 좌표 대조 + SDK 도착 이벤트. 실제 도착·수동 안내 종료를 구분한다. |
| 도중 안내 종료 후 차박 시작 | 이번 변경 | 최신 P단이면 사용자가 직접 시작할 수 있다. 실제 도착 플래그를 조작하지 않는다. |
| 차박 대시보드 | 구현 | 실제 잔량, 남은 시간, 평균 소비 가정에 따른 종료 예상 잔량, 부족 안내를 보여준다. 실제 소비 전력/절감량 측정은 없다. |
| 공조 수동 제어 | SDK 코드 구현·실차 미검증 | 운전석 설정 온도 조회와 ±0.5°C 변경, 지원 범위/조절 단위/쓰기 권한/P단 확인, 변경 후 재조회. 현재 에뮬레이터는 HVAC 값이 제공되지 않아 비활성화된다. |
| 공조 자동 제어·자동 에너지 관리 | 미구현 | 잔량·소비 추세에 따라 온도/모드를 자동 조절하는 루프는 없다. ‘자동 관리 준비 중’으로 표시한다. |
| 귀가·여정 완료 | 흐름 구현 | 확인한 집 좌표로 실제 내비 경로 요청. 필요 시 목업 충전소 경유. 실제 귀가 주행·완료까지의 실차 검증은 없다. |

## 4. 현재 전력 계산값

- 현재 사용 가능 에너지 = 실제 SOC × 설정된 배터리 용량.
- 배터리 용량 기본 60kWh, 전비 기본 5km/kWh. 두 값은 실제 차량 측정값을 자동 읽는 것이 아니라 계획 설정값이다.
- 가는 거리: 목업 20/50/90km.
- 차박 소비: 평균 1.2kW × 계획 시간. 냉난방 세기·외기온·설정 온도에 따라 바뀌는 모델은 없다.
- 귀가 거리: 선택 차박지와 확인한 집 좌표의 직선거리 × 1.3. 실제 도로 거리가 아니다.
- 예비 배터리: 전체 용량의 10% 고정. 이전 22% 하한은 제거했다.
- 필요 에너지 = 가는 이동 + 차박 중 사용 + 귀가 + 예비 배터리.
- 추가 충전 = max(0, 필요 에너지 − 현재 사용 가능 에너지).
- 100% 충전으로도 부족한 계획, 경유 충전소에 도달하지 못하는 계획을 구분한다. 충전소까지의 가는 거리는 현재 5km 가정이다.

현재 계획 시간은 ‘전력 계획 확인 시점부터 다음날 출발까지’라 이동 시간도 포함한다. 도착 후 순수 체류 시간과 다르다. 차박 타이머는 앱 비가시 구간의 실제 경과 시간을 완전히 복원하지 못한다. 수동 차박 시작 시에도 귀가 추정의 기준 좌표는 아직 선택한 목업 차박지다.

## 5. 실제 사용 SDK와 라이브러리

### Pleos SDK

| SDK | Gradle 선언 버전 | 실제 사용 |
|---|---|---|
| ai.pleos.playground:Vehicle | 2.3.2 | EV 배터리 SOC, 기어 P단, 운전석 HVAC capability/설정 온도/쓰기 및 재조회 |
| ai.pleos.playground:NaviHelper | 3.0.5 | 현재 위치, HOME 즐겨찾기, 집 등록 화면, 목적지/경유 경로 요청, 안내 상태, 도착/취소 이벤트, 내비 Foreground 요청 |

설치된 에뮬레이터에서 내비 공급자/데이터 버전 3.0.4 응답을 확인했다. 앱이 선언한 NaviHelper 3.0.5와 공급자 버전을 혼동하지 않는다.

FusedLocation SDK는 현재 의존성에 포함되어 있지 않다. Google Maps·Google 위치 SDK·Firebase·AI/LLM SDK도 현재 기능 구현에 사용하지 않는다. 장소 추천은 AI 추천이 아니다.

## 6. 아키텍처·작동 구조

- UI: MainActivity, JourneyScreen, HomeScreen, DepartureScreen, TravelScreen. 상태와 사용자 동작을 받아 화면을 표시한다.
- 상태/흐름: CampilotViewModel + CampilotUiState(StateFlow). 장소 선택, 집 확인, 시간, 계산, 경로, 차박·귀가 단계를 관리한다.
- 계산: JourneyBudget / EnergyCalculator / HomeDistanceEstimate. SDK 호출과 별개로 계산한다.
- SDK 어댑터: PleosVehicleGateway, PleosNavigator, PleosHomeGateway, LiveLocationPanel의 위치 연결.
- 저장: PlanStore(DataStore). 현재 여정·집 확인 상태·내비 세션은 메모리에 있으며 프로세스가 종료되면 전체 복구하지 않는다.
- 이동 유지: NavigationSessionService가 사용자 출발 동작에서만 foreground session을 시작한다. 실제 SDK 리스너는 ViewModel이 수집하는 경로별 Flow에 있다.
- 요청별 세대 번호와 리스너 해제로 이전 요청의 늦은 응답이 새 여정을 바꾸지 않도록 한다.

## 7. 추가 구현 우선순위

### 우선순위 1 — 추천·계산의 실제 데이터 전환
1. 현재 위치에 따른 실제 캠핑장 검색·거리 정렬·차량 숙박 가능 여부/시설 정보 연결.
2. 실제 충전소 위치·충전기 종류·가용성 데이터와 경유 우회 거리 반영.
3. 실제 도로 경로 기반 이동/귀가 거리 확보. 현재 SDK의 임의 출발점 제약을 고려해 별도 경로 데이터 수단을 검토해야 한다.
4. 수동 차박 시작 시 실제 주차 위치를 저장하고 그 위치에서 집까지의 귀가 전력을 다시 계산.
5. 실제 도착 시각부터 다음날 출발까지 체류 시간을 재산정하고, 백그라운드·재시작 경과 시간 복원.

### 우선순위 2 — 차별화 기능인 자동 에너지 관리
1. 냉난방 사용량·차량 기본 소비를 실측해 평균 1.2kW 가정을 보정.
2. 외기온·설정 온도·차종·시간에 따른 소비 예측 모델을 만들고 오차 범위를 표시.
3. 사용자 허용 온도 범위, 귀가 전력, 예비 10%를 함께 고려하는 자동 공조 제어 루프.
4. 수동 공조 변경 시 자동 제어 일시 중지, 제어 실패/정보 지연 시 중단, 변경 이유 표시.
5. 계획 대비 실제 잔량 추세를 비교해 체류 단축·충전·귀가 등 다음 행동을 제안.
6. 실내 실제 온도·설정 온도·소비 전력을 서로 다른 값으로 취급하고 SDK 지원 여부부터 확인.

### 우선순위 3 — 실차·복원·시연 완성도
1. 실차 HVAC 지원·권한·온도 영역/단위와 도착/경유지/귀가 이벤트 검증.
2. 앱 프로세스 종료 후 진행 단계, 선택 장소, 집, 출발 시각, SDK 세션을 복원.
3. 차종별 백그라운드 서비스·알림·앱 복귀 정책 검증.
4. 목적지/경로 변경 및 사용자 내비 조작과 앱 여정 불일치 처리.
5. 현재 목업 장소/추정 소비와 실제 차량값이 사용자에게 분명하게 구분되는 시연 자료 작성.

자동 창 동시 배치는 후속 검토 항목이다. 현재 에뮬레이터에서는 실패했으므로 지금은 내비 안내 종료 후 앱 복귀 방식을 사용한다.

## 8. 이번 변경 검증
- assembleDebug / assembleDebugAndroidTest 통과.
- NavigationHandoffTest 집중 기기 테스트 1개 통과: 안내 중 시작 불가, 종료 후 수동 시작 허용, 비P단·오래된 값 거절, 재안내 시 종료 상태 초기화, 실제 도착 플래그를 바꾸지 않고 STAY 전환.
- 테스트는 실제 Pleos 배터리/P단과 제어된 내비 이벤트를 사용했다. 실제 내비 도착 주행 시험은 아니다.
- 전체 테스트와 전체 린트, 추가 실제 내비 주행 반복은 하지 않았다.
- APK는 에뮬레이터에 설치하고 [최신 APK](../artifacts/Campilot-navigation-debug.apk)에 반영한다.

Gradle 질문: “Do the app and manual-stay navigation-end test compile after allowing parked users to start camping?” — 성공. gradle-run wrapper를 사용했으며 finish는 wrapper 소유 로그만 정리한다.
